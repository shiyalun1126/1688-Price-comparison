### 第 2 章 相关技术（约 2,500 字）

四节，每节都按「是什么 → 本文为什么用它 → 用它带来的代价」写：

1. **多模态大模型图像理解**：视觉判定替代感知哈希/CLIP 相似度的原因（同款判定要理由，不要分数）；代价是延迟与 token 成本。
2. **ReAct 与 function calling**：13 个业务工具如何被自主编排；代价是轨迹不可预测，需落库审计（`agent_run` / `agent_plan`）。
3. **对话状态机**：为什么不用纯 LLM 自由对话（不可控、会重复提问、会被平台判定为机器人），而用 10 态状态机约束 LLM。
4. **Chrome DevTools Protocol 浏览器自动化**：为什么不用 Selenium/HTTP 直采（登录态、动态渲染、风控）。

**这一章最容易写水。** 判断标准：删掉任何一节，你的系统还能不能讲清楚？能，就说明那节在凑字数。

### 第 3 章 需求分析与总体设计（约 3,000 字）

- **3.1 需求分析**：两类角色（小批量买家 = 同款谁便宜；大宗进货方 = 报价条件与议价空间），各 3–4 条用例。用例要能对上界面截图。
- **3.2 总体架构**：四层——采集层（书签导入 / CDP 搜索）/ 判定层（视觉 + 规则降级 + 分层）/ 议价层（询价状态机 + 谈判引擎）/ 呈现层（看板 + 导出）。画一张分层图，标注每层对应的模块名。
- **3.3 数据模型**：11 张表，重点讲 4 张：`target_style`、`product`、`inquiry_session`、`quote`。要说明**为什么报价和商品分开存**（一个商品可以被多次询价，报价有版本与条件）。
- **3.4 关键流程**：一张时序图，从录入目标款到输出比价结论。

### 第 4 章 关键方法设计与实现（约 4,500 字）★ 论文核心

这一章决定论文是"系统实现"还是"有方法的工作"。四个小节：

**4.1 分层同款判定方法**
- 双阈值复核：`RECHECK_LOW=0.45` / `RECHECK_HIGH=0.75` 之间触发二次判定，`merge_recheck` 合并两次结果。要写清楚**为什么中间置信区间要重判**（模型在"看不清细节"时倾向给中间值，单次判定等于赌）。
- 品类自适应提示词：`build_system_prompt(category)` 按品类注入比对维度。
- 规则降级：视觉失败/缺图时走 `_rules_verifier` + `_has_attribute_evidence`，并说明降级结果**不进硬比价**（只标"未核验"）。
- 三档分层：exact / equivalent / rejected / no_image，为什么只有 exact 参与硬比价（这是"可比性"的形式化）。
- 增量复用：已判定商品跳过，`image_scores` 召回 + 8 线程并发。

**4.2 缺口驱动的多轮询价决策方法**（本文主要贡献点）
- 问题形式化：把询价建模为**带缺口集合的部分可观测过程**。状态 $S = (Q, G, H)$：报价 $Q$、缺口 $G$、历史 $H$。动作空间 $A = \{$追问(g)、议价(p)、等待、转人工$\}$。
- 缺口计算 `compute_gaps`：7 个字段（价/MOQ/税/运费/现货/时效/阶梯价）。**要点**：`price=0` 不等于"其他字段也白问"；阶梯价只在「采购量 ≥ 100 且卖家报的是拿样档（moq ≤ 10）」时才追加——这是"量级对齐"，写进论文是很漂亮的一笔。
- 增量合并 `merge_quote`：非空才覆盖，因为卖家习惯分 3 条说完（先价、再 MOQ、最后运费）。对比"每轮覆盖"的朴素做法，这是明确改进。
- 意图识别 `classify_reply`：6 类（off_channel / suspect_bot / ask_which / calling / refuse / pending / normal），**判定顺序本身有设计意图**（先判站外引流最该停手，再判问款有明确动作）。要写明为什么用规则不用 LLM：可解释、零 token、可回归测试。
- 议价策略：`should_bargain` 门槛（价差 ≥ `bargain_min_gap`）→ `bargain_target = min(市场最低, 心理价) × 0.99`。**锚点必须来自库内真实报价**，不虚构（合规与可信度双重理由）。
- 收敛与退避：`backoff_seconds` 退避阶梯、`max_rounds=6`、`pending` 等待 ≥180s。
- 外发质量控制：`parse_model_message` 三级校验（标记提取 → 净化 → 元指令检测）+ 悬空尾巴拦截。**这一条是工程亮点，别当细节写**——它解决的是"LLM 生成内容直接外发"的可靠性问题，可以单独一小段。

**4.3 比价归一与结论生成**
- 标价与报价合并（报价优先），量级对齐（拿样价 vs 批发价必须问到同档才可比）。
- 输入指纹缓存：数据不变零 LLM 调用。报命中率。
- 结论三件套：综述 / 采购建议 / 议价话术，LLM 生成 + 规则兜底。

**4.4 风控与合规边界**（本科论文写这一节会加分，因为显得想清楚了工程的现实约束）
- 批量上限 8 家、每日配额 25、随机静默、按店铺去重；
- 命中验证码全局暂停，不自动破解；
- 站外引流一律转人工；
- 只用本人账号、小规模、非商用。

## 四、实验设计（三个实验，缺一不可）

### 实验 5.1 同款判定准确率 + 消融

**现状问题（必须先修）**

```
标注集：36 条
  different   30 条
  equivalent   6 条
  exact        0 条   ← 致命：核心类别零样本
  reviewed 全为 false  ← 跑出来的数字只是回归基线
目标款：仅 2 个（POLO 衫 20 / airpods 16）
```

`exact` 是本文"分层可比"的核心类别，一条样本都没有，等于核心主张无法被验证。

**补做动作**

1. 扩充到 **≥120 条**，三类均衡（每类 ≥35），覆盖 **≥5 个品类**（服装、数码配件、家居百货、鞋包、美妆工具）。
2. 全部人工复核，`reviewed: true`。复核标准写成文档（判 exact 的条件、判 equivalent 的条件），避免"凭感觉标"——答辩时这就是标注规范。
3. 跑 `python -m scripts.eval_accuracy --reviewed`，产出混淆矩阵 + 各类 P/R/F1。

**消融设计**（这是"方法有效性"的证据）

| 配置 | 说明 |
| --- | --- |
| A. 纯规则 | 只用 `_rules_verifier`，不调视觉 |
| B. 纯视觉单次 | 只调一次 `compare_images`，不做中间区间复核 |
| C. 视觉 + 双阈值复核 | 加 `RECHECK_LOW/HIGH` 复核 |
| D. C + 规则降级（本文完整方案） | 缺图/失败时降级并标"未核验" |

预期结论：A 在 exact 上召回高但精确率低（规则认标签不认货）；B 在拍摄差异样本上误判；C 提升中间区间准确率；D 覆盖率最高。**如果 D 没有明显优于 C，就如实写"降级只提升覆盖率不提升准确率"**——诚实的不显著结论远比编造的好结论安全。

工作量：标注 1.5–2 天，跑实验 0.5 天。

### 实验 5.2 多轮议价策略对比（论文最值钱的一张表）

**现状问题**：真实谈判会话 4 条，仅 2 条有卖家回复（13 条 / 9 条消息）。这个样本量做不了统计对比。

**解决思路：真实序列 + 离线重放**

仓库里已有 `scripts/verify_multiround.py`，能把真实卖家回复按序重放给 `decide()`，不联网、不发消息、不落库。把它扩成**三策略对照器**，是本科阶段性价比最高的一步。

三种策略：

| 策略 | 描述 | 对应现实做法 |
| --- | --- | --- |
| S0 单次长提问 | 一条消息把 7 个字段一次问全 | 常见"AI 写话术"工具 |
| S1 固定模板 | 按固定顺序逐项问，不判断卖家答没答 | 脚本化询价 |
| S2 本文（缺口驱动） | 只问缺的 + 增量合并 + 拿市场最低价锚点议价 | 本系统 |

**控制变量**：同一卖家回复序列、同一商品、同一采购量、同一 LLM 模型与 temperature、同一退避参数。

**指标**（全部可从库里算，不需要人工判分）：

1. **平均轮次**（rounds）
2. **字段完备率** = 最终拿到的字段数 / 7
3. **重复提问率** = 重复问已回答字段的次数 / 总提问次数 ← 这是 S2 相对 S1 的核心优势
4. **最终报价降幅** = (首轮报价 − 最终报价) / 首轮报价
5. **越界率** = 含元指令/悬空残句/重复内容的发送占比 ← 你独有的指标，体现外发质控
6. **完成率** = 拿到完整报价并正常收敛的会话占比

**样本要求**：**≥30 条**卖家回复序列。

获取方式（两条腿走）：
- 真实：再攒 **8–10 条**完整会话（每条 20–40 分钟，需本人配合过验证码）。这是最有说服力的部分，也是案例研究的素材。
- 构造：从真实会话中抽取回复片段，按「信息逐步披露」的典型模式拼装（先价 → 再 MOQ → 再运费 → 最后让价），并**明确声明为构造序列**。真实序列做主结果，构造序列做敏感性分析——这样写不会被质疑造假。

工作量：扩脚本 1 天，攒数据 1–2 周（碎片时间），跑实验 0.5 天。

## 七、答辩防守（六个必问题 + 答法）

**Q1「你的创新点是什么？」**
不要说"我做了个系统"。答：三个具体改进 + 一个数字。示例：「同款判定上我把中间置信区间做了二次复核并引入规则降级，在 X 条标注集上准确率从 A 提到 B；询价上我不做一次性话术生成，而是按缺口逐轮追问，重复提问率从 X% 降到 Y%；议价锚点强制取自库内真实报价，避免模型虚构价格。」

**Q2「视觉判定凭什么可信？大模型不是会瞎说吗？」**
答：三重约束——① 双阈值复核，中间区间重判；② 只有 exact 进硬比价，equivalent 明确标注"未核验"不参与排序；③ 每条判定强制输出 reason 与 key_diff，人可复核。再加一句：我们不是追求 100% 准确，而是追求**错判不会污染比价结论**，这是分层设计的目的。

**Q3「自动给卖家发消息，违反平台规则吧？」**
这道题必须准备，不要含糊。答：① 仅使用本人账号、小规模（单批 ≤8 家、日均 ≤25）、非商用；② 遵守频率约束与随机静默，模拟人工节奏；③ 命中验证码等风控信号立即全局暂停，不破解；④ 卖家引导站外交易、表达拒绝、怀疑是机器人，立即转人工。**主动承认这是灰区，并把边界写清楚**——比辩解"不违规"安全得多。

**Q4「数据从哪来？真实吗？」**
答：475 个真实商品、344 家真实店铺、30 次真实询价，采集自本人账号的公开搜索结果页与真实会话；标注集人工复核；构造序列部分（若有）单独声明。

**Q5「跟现有比价工具/插件有什么区别？」**
答：现有工具比的是**标价**，且认为搜索结果里的商品可比。本文解决两个它们不解决的问题：同款是否真同款（分层判定）、价格是否是真实成交价（询价 + 量级对齐）。**量级对齐这个点要讲**——「1 个起批 56.9」和「200 件 47」直接比是错的，这是真实的坑。

**Q6「系统能跑吗？现在演示一下」**
准备离线可跑路径：`INQUIRY_CHANNEL=mock` + 内置剧本，3 分钟跑完询价→追问→议价。真实通道演示要提前准备登录态，并准备好验证码拦截时的说辞（"这里需要人工过验证，我们切到录屏"）。
